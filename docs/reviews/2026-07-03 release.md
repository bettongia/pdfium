## Blocking Findings

### 1. `packages/betto_pdfium/pubspec.yaml` omits `windows` from `platforms:`

> Completed

Lines 15–20 declare `macos, linux, android, ios, web` but not `windows`. Windows
x86_64 is the headline item in the dev.3 CHANGELOG, is tested green on
`windows-latest` in CI, and is marked "Supported" in both READMEs and
`version_pdfium.json`. Pub.dev derives its platform badges and search filters
from this field — the package would advertise **no Windows support** in the
release that adds it.

**Fix:** add `windows:` to the `platforms:` map. One line.

### 2. Stale platform table in `PdfDocument` class doc comment

> Completed. Note: the initial pass fixed the platform table (Windows added,
> "(pending)" removed from Web) but left the concurrency paragraph stale,
> still describing web as synchronous main-thread and pointing at a
> nonexistent `plan_layout_aware_reordering.md`. Follow-up edit corrected the
> paragraph to describe the shipped Web Worker + `postMessage` protocol,
> matching `README.md`.

`packages/betto_pdfium/lib/src/document/pdf_document.dart` lines 86–92 — the
class-level dartdoc, the first thing a reader sees on pub.dev — still says:

- `| Web | PDFium WASM (pending) |`
- `| Windows | Not yet supported |`
- "On web, PDFium runs synchronously on the main thread in v1 — a Web Worker
  path is deferred to `plan_layout_aware_reordering.md`."

All three are false (Windows shipped, WASM shipped, Web Worker offload shipped),
and the last line points at a nonexistent plan file. This contradicts the
accurate wording already in `README.md`.

**Fix:** update the platform table and concurrency paragraph to match
`README.md`'s current description of the Web Worker backend.

## Test Suite Assessment

Strong. 22 test files cover metadata, text/image/annotation extraction, search,
TOC, thumbnails, rendering, the WASM engine, worker RPC failure paths, bitmap
utils, date parsing, and real-world arXiv PDFs. Coverage is enforced at >=90%
for both VM (`make coverage`) and web (`make web_coverage`, correctly scoped to
`*/betto_pdfium/lib/*`, reporting 92.8% per the roadmap doc). The earlier web
coverage measurement bug (counting third-party JS, misleadingly reporting 39%)
was found and fixed.

Gap: no on-device/emulator tests in CI, so the mobile FFI load path and the iOS
xcframework symbol resolution are unverified per-commit.

## CI/CD Assessment

Functional and green, with two structural weaknesses:

- **Medium risk (accepted, kept as-is):** the native `test` matrix has
  `continue-on-error: true` (`.github/workflows/cicd.yml` line 59). A red
  macOS/Windows/Linux-arm run does not fail the workflow. Maintainer decision
  (2026-07-03): keep this intentionally — it lets all three platforms run to
  completion in a single CI pass so a failure on one platform doesn't hide
  results for the other two, which is more useful for triage than fail-fast
  gating. This is a deliberate tradeoff, not an oversight.
- **Advisory:** no mobile jobs — iOS/Android regressions can't be caught
  pre-merge.

Positives: `verify-wasm-worker` diff-checks the checked-in compiled worker
against its Dart source (prevents a silently-stale artifact shipping); PDFium
binary and WASM assets are cached; Pages deployment is gated to `push` only.
